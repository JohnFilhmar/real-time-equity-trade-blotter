PART ONE. FOUR DEFECTS THE OWNER FOUND BY USING THE APP.

  Each was checked against the code before being written down here. Verify each yourself before
  fixing, and say so if you find the diagnosis wrong.

  1.1 BROADCAST-DRIVEN REFETCH STORM, causing 429s. This is the most serious item in this document
      and it undermines the system's central claim.

      frontend/src/lib/query/settle_trade.ts lines 31 to 33 run on every broadcast and call
      invalidateQueries on trade_keys.events(tradeId), position_keys.all and event_feed_keys.all.
      The audit feed is a useInfiniteQuery, and invalidating an infinite query refetches every page
      currently loaded. Five loaded pages means five HTTP requests per broadcast. The live feed
      emits every 3 to 8 seconds. Opening the audit trail and waiting therefore produces a request
      storm and trips the rate limiter.

      Two things are wrong, not one. The requests are needless, and the "real time" claim is false
      for the positions and audit views, which are actually poll-on-event over HTTP.

      The broadcast envelope already carries the whole trade. Positions are derivable from it. An
      audit row is derivable from the trade plus the action that produced it. Neither needs a fetch.

      Do not pick the fix. Put the owner a written comparison of at least these, with cost and
      risk for each, and your recommendation:
        a) derive both client-side from the existing broadcast, adding no server surface
        b) broadcast the audit event itself as a new typed socket event, and apply it client-side
        c) keep invalidation but never on an infinite query, patching page zero instead
        d) leave the fetch but debounce or coalesce it
      Say explicitly which option makes the positions and audit views genuinely socket-driven
      rather than HTTP-driven, because that is what the owner is asking for.

      Separately, report whether the rate limits themselves are mistuned. A limit that an app trips
      during ordinary use is either the wrong limit or the wrong client behaviour, and the owner
      should be told which one you think it is.

  1.2 LOGIN ERROR SHIFTS THE LAYOUT. frontend/src/components/auth/LoginForm.tsx renders the error
      conditionally with nothing reserving its space, and passes error={undefined} to both Field
      components, so an error appears as a new block and pushes everything below it down.

      Reserve the space so the form does not move. Check whether the same pattern exists in the
      trade ticket and anywhere else Field is used, and fix it consistently rather than only here.

  1.3 PASSWORD REVEAL TOGGLE. The owner asked whether this is bad practice in a trading system. It
      is not; it is recommended practice, because masking drives typos and lockouts. Build it.

      Default to masked. Make it a real button, not a div, with aria-pressed and an accessible name
      that changes with state. Keep it out of the tab order between the field and the submit button.
      Do not auto-unmask, and do not persist the revealed state.

      Load the web-design-system and web-design-guidelines skills before touching this, and the
      backend-security-baseline skill before you change anything on the auth path.

  1.4 POSITIONS SHOWS A FLAT COLOURED BAR, NOT A LINE GRAPH PER RECORD. The owner compared this to
      the prototype and is right that they differ. It is not a component bug.

      frontend/src/components/positions/PositionsScreen.tsx contains no SVG and no sparkline. The
      coloured line is the "Share of gross" column, a proportion bar. GET /positions returns
      aggregates only: net quantity, bought, sold, gross notional, trade count. There is no time
      series, so there is nothing to plot. The prototype's per-record line was fed by its in-memory
      mark feed, which decision D2 said to build and which never landed on the server.

      So this is a scope question, not a fix. Put the owner the options: build the server-side mark
      feed so a real series exists, plot something derivable from data you already have, or keep the
      proportion bar and note the divergence from the prototype in the README. Give the cost of each
      and remind him that the research ranked P&L last of twenty-eight items on marks per hour, so
      he is choosing with that in front of him.

PART TWO. THE DELIVERABLE GAP IN database/.

  The brief lists database/ as a deliverable. It currently holds one README.md, while the schema,
  migrations and seed live in backend/prisma/.

  The owner asked whether the database should run separately rather than integrated with the Express
  server. It already does: Postgres runs as its own container in docker-compose.yaml, reached over
  DATABASE_URL. Nothing needs to change about how it runs, and confirm that in writing so the point
  is closed.

  Do NOT relocate the Prisma schema. prisma.config.ts, the generate output path, the migrate
  commands, CI and the Docker migrate service all resolve from backend/, and moving it breaks a
  fresh clone for no grading benefit.

  Propose to the owner what database/ should contain instead so it reads as a real deliverable: the
  ERD, every table and index with the reason it exists, the append-only trigger, the migration list
  and how to run them, the seed strategy, and a pointer to the canonical Prisma location. Get the
  contents approved before writing it.

SETUP

  A fresh worktree needs all three before anything runs:
      npm install
      npm run build:shared
      cd backend && DATABASE_URL="postgresql://x:x@localhost:5432/x" npx prisma generate

  Skip the last and typecheck fails on a missing generated/prisma/client.js. Skip the first two and
  the suite fails with `instruments` undefined. Neither is a real defect; both have been mistaken
  for one.

  The worktree guard refuses bash heredocs containing backticks and compound commands it cannot
  verify stay inside the worktree. Split into plain commands or use the Write tool. Most repo files
  are CRLF.
