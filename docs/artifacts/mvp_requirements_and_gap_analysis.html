How to read this

Every requirement below came out of research into how real blotters, real trade-capture APIs and real grading rubrics work, not out of the brief alone. Each one is then marked with what the repository actually does today, verified by reading the code on the branch that holds it.

No decision in here has been taken for you. Where the evidence points somewhere, it says so and names the cost of going the other way.

What the brief actually rewards

The rubric is weighted, and the weighting is the most useful planning document in the exercise. Engineering Quality 30, TypeScript 20, Full Stack Design 20, User Experience 10, Testing 10, Communication 10. The first three are seventy percent of the mark and none of them is a feature count. The brief says so in its own words: it does not expect production-ready systems, and it values thoughtful trade-offs and clear communication over feature completeness.

That points the opposite way from instinct. Nothing in the evidence rewards building more. The highest-value remaining work is narrow, finished, and written down.

The two lowest-value items on that table are both already designed

The interactive prototype ships a P&L view fed by a synthetic mark feed, and the design canvas carries Login.html and LoginMobile.html. Research ranks those 28th and 27th of 28 candidate work items. P&L is worse than low-value: it publishes a financial number derived from a mark price the brief never supplies and a cost-basis convention you would have to invent, to an audience who computes financial numbers for a living. Getting it wrong costs more than omitting it.

There is a cheaper way to bank the same domain credibility. Compute notional by symbol, Σ quantity × price signed by side, label it notional and not P&L, and put one line in the README saying real P&L needs a mark and a cost basis and both are out of scope. That sentence demonstrates more understanding than a wrong number does.

S-M23, the two seed defects

The generator does the hard parts well. Prices drift around a per-instrument base rather than being drawn at random, quantities are round lots weighted toward smaller tickets, session times cluster at the open and the close, books follow the listing venue, and one trade in twenty is already cancelled so the status filter has something to find. That is better than most submissions manage.

Weekend sessions. generate_trades() builds five consecutive days from 2026-08-18. The fifth is Saturday 2026-08-22, verified. Weekend trade dates are on the standard list of tells that mark a dataset as generated. The fix is to step over weekends when building the session array.

London prices are in pounds, not pence. The universe carries HSBA.L at 9.82, BP.L at 4.36, VOD.L at 0.78 and SHEL.L at 28.14. The London Stock Exchange quotes in GBX, so those names print around 982, 436, 78 and 2814 on a real blotter. There is also no currency field anywhere in the schema, so a grid mixing EQUITIES_US and EQUITIES_UK shows two currencies in one price column with nothing to tell them apart. This is a decision, not just a fix: see D7.

Server requirements: won't, and why

Each of these is a real technique that a reviewer might ask about. Naming them in the README with the reason scores on Communication, and builds the case that the omissions were priced rather than missed.

  • Idempotency-Key middleware with a fingerprint store. The unique constraint on tradeId plus a version-guarded amend already covers double-click and retry.
  • ETag and If-Match. The version field in the body is equivalent here and cheaper to get right. A half-built ETag layer, weak tags used with If-Match or 409 where 412 belongs, reads worse than none.
  • SERIALIZABLE isolation or SELECT FOR UPDATE. Optimistic concurrency fits low-contention amendments and needs no retry loop or lock ordering.
  • Socket.IO connection state recovery. Best-effort by its own documentation, capped by a disconnection window, and unsupported by the Redis pub/sub adapter. Refetch-on-reconnect has to exist anyway, so build the fallback first.
  • Redis adapter and sticky sessions. Single node here. Name the scale-out path instead.
  • Authentication. The rubric has no security line. See D3.
  • A partial index on status = 'ACTIVE'. Prisma emits parameterised predicates, and the Postgres planner cannot prove a parameter implies a literal index predicate, so the index would rarely be used. A talking point, not a win.
  • Allocations, confirmation, affirmation and settlement. The post-trade chain is a project, not a feature.
  • A FIX engine. Model the vocabulary, do not implement the transport.

The accessibility gap the design reference does not cover

Three markers are absent from the prototype entirely: role="grid", aria-sort and aria-live. So the grid has no ARIA grid semantics, a sorted column is not announced, and nothing announces that rows changed underneath the user. Combined with U-M4 and U-M12, the screen-reader and keyboard story is the weakest part of an otherwise strong design. It is also the cheapest to fix, because the WAI-ARIA grid pattern prescribes exactly what to do: one tab stop, roving focus inside, arrows between cells.

Interface requirements: should

Each is a visible step up costing roughly 30 to 120 minutes.

  • A quick filter across all columns, debounced, with a "showing 42 of 1,280" count.
  • Active filters as removable chips.
  • Multi-column sort by shift-click, with a stable tiebreaker on trade id so equal rows never swap under live updates.
  • Sort does not re-order on every tick. Only on load and on explicit user sort. If rows re-sorted on each update the grid would churn and nothing would be clickable. AG Grid declines to re-sort on value change for exactly this reason.
  • A pending row state for an optimistic amend, and a distinct failed state. Failed means the server said no. Conflicted means the server said "not from this version", which needs a diff, not a retry.
  • A row being edited is never overwritten by an incoming update for that row.
  • Recover from a rejected patch by replaying remaining patches over the last confirmed server state, not by surgically reverting. Surgical reversion drifts; rebasing cannot.
  • Never flash your own optimistic write and then flash again on confirmation. One user action producing two flashes looks like two trades.
  • A staleness ladder, live to degraded to stale, with an explicit "data as of 12s ago". Stale data is harder to spot than missing data, because the screen still shows a number.
  • A pinned summary footer with row count and total notional, recomputed on filter.
  • Clipboard copy as TSV that pastes into Excel, or a CSV download. Excel is where reconciliation happens.
  • Up and down colour tokens that can be inverted, because China, Japan and Taiwan use red for rising and green for falling, and Korea often uses blue for down. TP ICAP has a large APAC presence, so this is a live concern rather than trivia.
  • prefers-reduced-motion suppresses the flash animation while keeping the direction glyph. Already present in the prototype.
  • Density toggle, persisted. Doubles as a low-vision escape hatch, which is also how the tension between 24px rows and the WCAG 2.2 target-size minimum gets resolved.

Interface requirements: won't

  • A phone-optimised card blotter. A blotter is a desk tool on multiple monitors. Make the grid not break at 400px, say plainly that the phone target is read-only status, and do not pretend it is mobile-first.
  • Saved and named views. A real desk feature, but it is persistence plumbing rather than UX signal.
  • Field-level three-way conflict merge. Show the conflict and let the user choose. Auto-merge is a week of edge cases.
  • Column grouping, pivoting and aggregation rows. Grid-vendor enterprise territory.
  • Full WCAG 2.2 AA conformance. Name the known tension between compact rows and the 24px target-size minimum, and say the density toggle resolves it. That sentence scores better than a silent partial pass.

The backend agent and the design agent each made coherent choices. Five places where those choices do not meet.

One earlier conflict is already settled and should stay settled. The design shows an amended trade as ACTIVE plus an amber version pill, not as a third AMENDED status. Vocabulary worth using, and worth avoiding

TP ICAP is the world's largest interdealer broker, and since December 2024 has been migrating most of its infrastructure to AWS, co-developing its Fusion platform with an embedded AWS team. Its front-end job ads name React and TypeScript. The reviewer is likely to be someone who brokers these trades for a living, so correct jargon lands and decorative jargon does not.

Safe and useful. Trade capture, which is the industry name for what the POST endpoint does, and is literally the FIX TradeCaptureReport <AE> message. Notional. Net position by symbol. Trade lifecycle. Book. Counterparty. Amend, cancel and bust, used precisely: a cancel is the firm withdrawing its own trade report on trade date, a reversal is the same act afterwards, and a bust is a venue declaring a trade clearly erroneous under FINRA Rule 11891.

Avoid unless certain. Matched principal, name give-up, clearing, settlement date, T+1, best execution, RFQ. All real TP ICAP vocabulary, but this exercise has no settlement or clearing dimension, and using them decoratively reads as keyword-stuffing.

Method and sources

Four parallel research passes, roughly 100 searches and fetches between them, covering the blotter domain and FIX lifecycle, real-time grid UX, server and real-time architecture, and what scores on a take-home at a trading firm. Every status column above was then checked against the code by reading it on the branch that holds it, not by trusting the handoff notes. Two claims were verified by execution: the Saturday session date, and the absence of ARIA grid markers and tick-arrow glyphs in the prototype source.

Primary sources include the FIX 4.4 dictionary for tag numbers and the ExecType and TradeReportType enums; 17 CFR 240.17a-3 and 17a-4 for what a blotter is as a record and how long it is kept; FINRA Rules 11891, 7130 and 4511; SEC Rule 15c3-5 on pre-trade controls; the Socket.IO documentation on delivery guarantees, connection state recovery and CORS; RFC 9110 and RFC 9457; the PostgreSQL documentation on transaction isolation, numeric types and partial indexes; Google AIP-158 on page tokens; AG Grid on flash timings, DOM virtualisation and high-frequency updates; W3C WCAG 2.2 and the WAI-ARIA grid pattern; Nielsen Norman Group on data tables, response times and skeleton screens; and Bloomberg's published work on designing the Terminal for colour accessibility.

Known limits. Vendor blotter column lists from Bloomberg AIM and TOMS, Charles River and Fidessa are behind logins and could not be verified. The MiFID II RTS 25 clock-synchronisation figures come from a secondary source cross-checked against vendor whitepapers, not from EUR-Lex directly. No public TP ICAP engineering rubric exists, so the grading section is drawn from published rubrics elsewhere plus reviewer writeups, with inferences labelled as such in the underlying research.
