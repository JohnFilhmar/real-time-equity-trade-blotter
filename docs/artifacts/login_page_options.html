Six ways to build the front door of the desk, each running live below with the app's own tokens, and the four choices that cut across all of them: what shows at zero milliseconds, whether there is a splash, how much moves, and what the form does for the person typing. What the door must keep

These are recorded decisions or measured facts. Every layout below honours all of them, so none of them is a differentiator.

  • The form never moves when an error appears. The two-line error slot is reserved (FieldError, measured 0px shift in the hardening pass). The checkbox above proves it per layout.
  • Password reveal is the lucide eye on a real button, aria-pressed, outside the tab order. Reused as-is.
  • Three themes. Dark is home, light and system follow the OS or a stored choice; the theme boot script runs before first paint.
  • Copy register. "Sign in to the desk", "Desk credentials. Your trader code stamps every trade you book, amend or cancel." Sentence case, no marketing.
  • No self-service. No registration, no password reset. Trader codes are issued by the desk head. Every layout says so instead of hiding it.
  • Demo accounts stay visible for the assessor: jsmith, abrown, mjones, viewer, password in the README.
  • Reduced motion wins. The global rule collapses every animation and transition to a millisecond. Clocks still tick, because a clock is information, not decoration.
  • Nothing sensitive before sign-in. No trade rows, symbols, traders or counterparties on the door, even blurred. What is arguable (a broadcast counter, a readiness line) is listed as a question, not assumed.

What "private firm" reads as

The centred glass card is the generic sign-in of every SaaS product, and it is generic because it says nothing about where you are. A private system's door says five things without a paragraph of marketing:

  • Place. This is a specific desk: equity cash, London, one session, one clock. The page names it.
  • Control. Access is issued, not claimed. The words on the page are credential words, not account words.
  • Liveness. The system behind the door is running now: the UTC clock, the session state, whether the API is ready.
  • Restraint. One accent, one typeface pair, hairlines instead of shadows. Nothing sells.
  • Provenance. A build hash and the environment in the corner, the way a terminal carries its version.

Two things that read as a bank's website rather than a firm's system, and are avoided everywhere below: a photograph of a skyline, and a second decorative colour.

The choices that cut across every layout

Loading: what shows at zero milliseconds

Today RequireAnonymous renders nothing until the session-restore request answers, so the login page is a blank ground for the round trip of one POST /api/v1/auth/refresh. Locally that is tens of milliseconds; on a real link it is a visible blink of nothing. The gate exists for a good reason (a signed-in user must not be flashed a form on reload) and stays. The change is what the gate holds back.

OptionBehaviourCostRecommendation
L1 · hold everythingAs now. Blank until restore resolves.0hNo. It is the one loading defect every layout above inherits.
L2 · hold only the formThe stage (panel, clocks, statement, footer) renders during restore with the form's space reserved; the fields mount on anonymous. A signed-in user sees the stage for one round trip, then the blotter.0.5hrecommended Works for B, C, D and F; E has nothing static to show.
L3 · show the form disabledFields render immediately, disabled until restore resolves.0.5hNo. Reintroduces the flash the gate prevents, now with a disabled form on top.

Theme additions

The brief keeps the colour theme as it is and asks for more. "More" here means new tokens, never changed ones: every existing value in globals.css stays byte for byte, and the additions are used by the door and by empty states that share its emptiness. Questions for the owner

Nothing above is built. Each item names the recommendation and the skill or memory it was checked against.

  1. Layout. B, F, or C. Recommend B. Checked against web-design-system (Tailwind only, primitives reused, no per-page CSS) and frontend-design (one signature element, the living panel; no skyline, no second colour).
  2. Loading. L2, render the stage during restore and hold only the form. Recommend yes. Checked against the hardening decision that the form never shifts: the form's space is reserved while held.
  3. Splash. S0 before, S2 after submit. Recommend both. Checked against web-design-guidelines: progress as a live region, never a timer.
  4. Motion. M1. Recommend M1. Checked against the global reduced-motion rule in globals.css, which already collapses it.
  5. Theme additions. The five additive tokens, both themes, no existing value changed. Recommend yes. A second hue is a separate question; recommend no.
  6. Extras. Caps Lock warning, theme switch on the door, readiness line, lockout countdown. Recommend all four; the broadcast counter no. Checked against backend-security-baseline: nothing new is exposed before authentication; /ready is already public.
  7. Verification. Lighthouse on the login page re-run after the build, the four browser journeys unchanged, and a login-page journey added only if the layout adds behaviour (the handshake in C, the steps in D).
