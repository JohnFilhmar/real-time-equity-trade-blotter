Blotter Build Plan

Execution plan for a real-time equity trade blotter, starting from the bare Express and Next.js scaffold already committed. Decisions first, then the phase order that gets to a submittable state inside the 8–15 hour budget.

Stack Express 5 · Prisma 7 · Postgres · Next 16 · React 19 Budget ~12 h Window 7 calendar days

Decisions taken up front

Each of these is a graded trade-off. The rejected option matters as much as the chosen one, so both go in the README.

QuestionChosenWhyRejected
Database Postgres 17 + Prisma The compose file already sets read_only: true on the backend, which a SQLite file cannot survive. Postgres also lets the schema show real indexing and enum design. SQLite
Price column Decimal(18,6) Binary floats cannot represent a price exactly. On a trading blotter that is the first thing a reviewer looks for. Float, Double
Realtime transport Socket.IO Reconnection with backoff, rooms for later per-book scoping, and a typed event map through Server<ClientToServer, ServerToClient>. Raw ws, SSE
API contract Shared zod package One canonical schema per model in an npm workspace both apps import, so the request shape, the response type and the socket payload cannot drift apart. Duplicated types per app
Live update strategy Patch the query cache Socket events call setQueryData. Refetching the whole blotter on every event scales badly and reads as the lazy option. Refetch on event
Authentication Out of scope, documented Not a requirement. The transport hardening that does apply is kept; the JWT rotation and RBAC design is described in the README instead of half-built. Half-built login

The trade model

The brief states the model twice, and the two statements do not agree. The Trade interface names id and tradeDate; the sample payload names tradeId and tradeTimestamp, and adds book and counterparty, which the interface omits entirely.

Resolution: satisfy both, and say so in the README.

The interface is described as a minimum and the sample as the data the blotter actually consumes, so the sample is the wider contract and the interface is the floor. Carrying every field from both costs two extra columns and removes any question of whether the brief was read closely.

Field naming

The brief's payload is camelCase, and this repository's convention is snake_case for JSON fields. The brief wins at the wire, because it is a given contract and a reviewer comparing the response against their own sample should see the same keys. Everything the convention does own stays snake_case: database columns, file names, variables. Prisma's @map bridges the two in one place.

Indexes

Driven by what the blotter actually queries rather than added by reflex: a composite on (status, trade_timestamp desc) for the default view, single-column indexes on symbol, trader and book for the filters, and a unique constraint on trade_id.

What makes the seed realistic

The brief asks for realistic randomised data, and uniform random values are the obvious way to fail that while technically complying.

  • Prices start from each symbol's own level, taking the sample's figures as the anchor (AAPL near 227, MSFT near 534, TSLA near 341), then drift. A price of 12.40 on AAPL reads as random noise, not as market data.
  • Quantities are round lots, multiples of 100, skewed so small tickets outnumber blocks.
  • Timestamps fall inside a trading session and cluster at the open and the close.
  • Traders come from a fixed desk roster in the sample's own initial-plus-surname form (JSMITH, ABROWN, MJONES), and books correlate with the instrument's listing venue rather than being drawn independently.
  • Roughly 5% arrive CANCELLED, so the status filter has something to find.
  • 500 rows, inside the 100 to 1,000 the brief asks for, generated from a fixed seed so the dataset is reproducible between runs.

Phase order

Numbered because the order carries real dependencies: the shared contract has to exist before either side consumes it, and the service layer has to emit events before the frontend can subscribe to them.

  1. Foundation

    1.5 h

    npm workspaces, the shared/ contract package, validated env config, Prisma schema and first migration, Postgres in compose, and the scaffold defects above.

  2. API

    2.5 h

    Repository, service, routes. List with filter, sort and pagination; create; amend; cancel. Central typed error handler. Seed roughly 500 trades on startup when the table is empty.

  3. Realtime

    1 h

    Typed Socket.IO server emitting trade.created, trade.amended and trade.cancelled from the service layer, never from a route handler.

  4. Frontend blotter

    3.5 h

    TanStack Query, TanStack Table and virtualisation. Sort, filter, manual refresh, create and amend dialogs, cancel confirmation, optimistic updates with rollback, and designed loading, empty and error states.

  5. Tests

    2 h

    Unit on state transitions and schemas, supertest integration against a real Postgres, a two-client socket broadcast test, and one Playwright pass where a trade created in one tab appears in another.

  6. Bonus features

    1 h

    Audit trail written in the same transaction as the amend, and a net-position-by-symbol endpoint. Both are cheap and both are visible to a reviewer.

  7. Documentation

    1 h

    README covering architecture, setup, tests, assumptions and trade-offs, plus the AI usage report assembled from the prompt log.

Known risks

  • Workspace plus Docker. Moving to npm workspaces means both build contexts move to the repository root. Worth it for the contract package, but it is the change most likely to break the image, so it lands in phase 00 while there is time to fix it.
  • Pre-existing audit findings. npm audit reports five high severity issues, all reached through the Prisma 7 toolchain via @prisma/config. The suggested fix downgrades Prisma to 6.x, a breaking change, and the vulnerable paths are build-time rather than runtime. Documented in the README instead of downgraded.
  • Scope creep through bonus features. The exercise explicitly values trade-offs over feature completeness. Audit trail and positions are in; P&L, login and deployment stay out unless the budget survives phase 05.
